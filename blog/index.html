Part 1Recovering the Managed Payload from a Truncated .NET Single-File Bundle

01Introduction

For those unfamiliar with the technique, single-file deployment represents an evolution in how commercial .NET applications are distributed. Rather than shipping a manageable folder of DLLs, configs and a stub EXE — all of which scream “open me in dnSpy” — the entire payload is embedded into a single native executable. The target machine runs one host that extracts its own assembly graph into memory at startup. No clean folder structure, no Managed.dll sitting next to the exe, no obvious entry point for a managed debugger.

This approach creates a deceptively thick layer of protection: to a casual analyst, the 77 MB binary looks like a native C++ application. There’s a real PE with real imports, a plausible entry point, and none of the telltale .managed sections. Traditional “drop it in DIE and find the .NET module” workflows break down because the interesting payload is buried behind a native host you never asked for.

The particular target we were given — NoMercyAI.Visual-r2.exe — advertised itself as hardened. And on the surface, it wasn’t an unreasonable claim: 77 MB of native-looking code with an obfuscated managed core buried inside. But there’s a joke in the RE community that the best way to defeat an obfuscation is to ask for a copy of the plaintext. In our case, the app was kind enough to embed its own plaintext — encrypted, compressed, but very much present.

But sometimes the best way through a wall is to walk around it entirely, so let’s start from the beginning…

02Initial reconnaissance

To start this off, we could try to bruteforce our way in and make assumptions since this is a typical pay-to-cheat loader, but that wouldn’t make for a very good blog post. Instead, let’s analyze the binary and see what we can grasp about it — that’s always a solid starting point.

We begin by dropping the file into DIE and IDA to get our bearings. The file comes in at 77,363,498 bytes (~77 MB), which is already unusual — a cheat overlay should be a few hundred KB. That size delta is the first real hint that we’re dealing with something bundled, not something compiled. The native image base is 0x140000000 (standard x64), and IDA happily loads it as a native PE32+ host.

The most productive early move was simply scanning the binary for interesting strings. Two things immediately caught our eye:

  1. A reference to NoMercyAI.Visual.dll at offset 0x140797690, and
  2. The telltale signature strings of the .NET runtime host: hostfxr/mscoree exports, plus two SHA-like marker hashes at 0x6FB3B0 (c3ab8ff13720e8ad9047dd39466b3c89) and 0x6FB388 (74e592c2fa383d4a3960714caef0c4f2).

Those two hashes are the fingerprint of the .NET self-contained single-file host. The native entry points sub_140563D00 and sub_140563F60 (the bundle loader) reference the DLL name string directly. What we were looking at wasn’t a cheat that happens to be a native binary — it was the standard .NET 8 single-file bundle host with a 77 MB payload glued onto the back. The “native application” was a bootstrap.

That reframes the entire engagement. The question stops being “how is this native binary obfuscated?” and becomes “how do I pull the managed assembly graph back out of this bundle?”

03Anatomy of a single-file bundle

The .NET single-file format is well documented and, at a high level, simple. A single-file app is structured as:

[native host executable]
[bundle data...]
[bundle entry table]  <- metadata describing every embedded file
[bundle footer]       <- signature + offsets, right at EOF

Normally, an analyst simply reads the last 16 bytes of the file to find the footer — a magic marker (0x8b12), a flags value, and the file offset where the bundle header begins. From there, the entry table is parsed backwards and every embedded file can be located and extracted. It’s a solved problem; tools like dotnet-bundle-extract do it in seconds.

We did not have a normal file.

04Working around the missing footer

The first extraction attempts failed immediately. The file ends abruptly — its last bytes are the tail of the embedded NoMercyAI.Visual.deps.json name string, with no trailing NUL, no 0x8b12 marker, no footer fields. This file was clearly truncated or modified (the -r2 suffix in the filename is now suspicious in retrospect — this is a stripped or repacked copy).

A quick sanity check of the end of file:

tail_bytes.py 
# where does the file end, and is there a footer?
data = open(r"C:\Users\huget\Desktop\sss\REVERSING\NoMercyAI.Visual-r2.exe", "rb").read()

print("file size:", hex(len(data)))
print("last 16 bytes:", data[-16:].hex(" "))

# The .NET single-file footer signature is 0x8b12 as a little-endian marker.
marker = data[-16:].find(bytes.fromhex("8b 12"))
print("0x8b12 footer marker found at:", marker)
file size: 0x49c792a last 16 bytes: <truncated name bytes, no NUL, no footer> 0x8b12 footer marker found at: -1

Normally a missing footer is a dead end. But we had two facts on our side:

  1. The truncation point is recoverable. The bundle was cut off right after the last entry name, which means the data area is fully intact.
  2. The entry table survives. The bundle’s entry table is written before the footer, so even when the footer is gone, the table is usually still present — we just have to find it.

Scanning for the bundle signature GUID (e8280b8b…) turned up nothing. But a more pragmatic approach worked: the entry table has a distinctive structure, and the last entry’s relative offset plus its name length should land exactly at the end of the file if we’ve found the right start.

That’s how we found 0x49C101A.

05Decoding the entry table

At 0x49C101A we began parsing the bundle’s entry table. Each entry has a compact, consistent layout:

[rel_off   : u64]  absolute file offset of the embedded data
[uncomp    : u64]  uncompressed size
[comp      : u64]  compressed size (0 = stored, no compression)
[ftype     : u8 ]  file type tag
[len       : u8 ]  length of the name string
[name      : ...]  UTF-8 file name

The first step was to verify the structure by brute-forcing the start of the table. We tried every plausible alignment as a candidate origin and checked whether the final entry self-consistently terminated exactly at EOF:

probe_table.py 
# hunt for the entry table origin
import struct

data = open(r"C:\Users\huget\Desktop\sss\REVERSING\NoMercyAI.Visual-r2.exe", "rb").read()
EOF = len(data)

for origin in range(0x49B0000, 0x49C8000, 8):   # scan a window just before EOF
    pos = origin
    last_end = None
    ok = True
    entries = 0
    while pos + 25 <= EOF:
        rel_off, uncomp, comp, ftype = struct.unpack_from("<QQQB", data, pos)
        pos += 25
        nlen = data[pos]
        pos += 1
        name = data[pos:pos + nlen].decode("utf-8", "replace")
        pos += nlen
        entries += 1
        last_end = pos
        if rel_off >= EOF or uncomp > 0x20000000:
            ok = False
            break
    if ok and entries > 300 and last_end == EOF:
        print(f"[!] candidate origin: {hex(origin)}  entries={entries}  terminates at EOF")
[!] candidate origin: 0x49c101a entries=448 terminates at EOF

Reading forward from 0x49C101A, entry by entry, we hit a perfect EOF: 448 entries, and the final entry’s name ended precisely at the end of the file (0x49C792A). That self-consistency check is what confirmed we had the correct table origin. We hadn’t found the footer — we’d found something better: a complete, intact table.

06Compression: raw deflate, of course

The next detail mattered for extraction. For entries where comp != 0, the data is compressed. A quick check of the first bytes told us the compressor: raw DEFLATE — i.e., zlib streams with wbits=-15, the headerless variant with no zlib container. (We initially suspected Brotli, since modern .NET supports it, but the byte patterns and a deflate attempt settled it immediately.)

For entries where comp == 0, the data is stored verbatim. That mixed model is exactly what the runtime host does: hot managed assemblies get compressed, small text files (.runtimeconfig.json, .deps.json) often ride along raw.

07Extraction

With the table decoded and the compression identified, extraction became a mechanical exercise: seek to rel_off, read comp bytes, zlib.decompress(..., wbits=-15) to get uncomp bytes, write to disk under the entry name.

Here’s the actual script we used:

extract_final.py 
# full bundle extraction
import os
import struct
import zlib

INPUT = r"C:\Users\huget\Desktop\sss\REVERSING\NoMercyAI.Visual-r2.exe"
OUT   = r"C:\Users\huget\Desktop\sss\REVERSING\NoMercy-Crack\bundle"

TABLE_ORIGIN = 0x49C101A   # confirmed by self-consistent EOF termination

def main():
    data = open(INPUT, "rb").read()
    os.makedirs(OUT, exist_ok=True)

    pos = TABLE_ORIGIN
    ok = 0
    failures = 0

    while pos < len(data):
        # entry header: rel_off(u64) | uncomp(u64) | comp(u64) | ftype(u8)
        rel_off, uncomp, comp, ftype = struct.unpack_from("<QQQB", data, pos)
        pos += 25

        nlen = data[pos]; pos += 1
        name = data[pos:pos + nlen].decode("utf-8")
        pos += nlen

        raw = data[rel_off:rel_off + comp]

        # comp == 0 means the entry is stored raw; otherwise it's raw DEFLATE.
        if comp == 0:
            blob = raw
        else:
            try:
                blob = zlib.decompress(raw, wbits=-15)
            except zlib.error as e:
                failures += 1
                print(f"[FAIL] {name}: {e}")
                continue

        if len(blob) != uncomp:
            failures += 1
            print(f"[FAIL] {name}: size mismatch ({len(blob)} != {uncomp})")
            continue

        dst = os.path.join(OUT, name)
        os.makedirs(os.path.dirname(dst), exist_ok=True)
        with open(dst, "wb") as f:
            f.write(blob)
        ok += 1

    print(f"OK={ok} FAILURES={failures}")

if __name__ == "__main__":
    main()
OK=448 FAILURES=0

448 / 448 files extracted, 0 failures. No missing entries, no truncated streams, no checksum mismatches. The entire assembly graph — all the framework DLLs (Microsoft.CSharp.dll, etc.), the resources, the satellite localization files, the configs — recovered in a single pass.

08Validating the prize

The crown jewel, as expected, was NoMercyAI.Visual.dll (5,644,288 bytes). It validates as a proper PE32+ with a CLR header and the BSJB metadata signature at 0x533490 — a standard .NET 8 managed assembly, entirely intact. The supporting files came along perfectly:

At this point we had crossed the wall. The “impenetrable 77 MB native binary” was, from the perspective of the analyst, just a .NET host with a file cabinet welded to its back. The managed core — the actual product, the actual logic — was sitting on disk as a clean, loadable PE that dnSpy opens like a book.

09What’s Next?

We now hold the real NoMercyAI.Visual.dll, extracted cleanly from its loader. But the developers didn’t make it that easy to read. As we’ll see in Part 2, the managed core is obfuscated — class names reduced to single letters (A.a, A.B, … A.O), and every meaningful string (URLs, error messages, license states) encrypted and only decrypted at runtime through a dedicated decryptor class. Recovering those strings required decompiling the DLL and then executing the decryptor methods against the live assembly to dump all 453 strings — which is exactly where we’re headed.

Having 448 embedded files is just the beginning.

Part 2Defeating the String Obfuscation

01Introduction

In Part 1 we pulled the real payload out of the truncated single-file bundle: a clean 5.6 MB PE32+ managed assembly, NoMercyAI.Visual.dll, that dnSpy opens like a book. That was the hard wall. Or so we thought.

There’s a thing that happens right after a win like that: you open the DLL, you get your first decompiled class, and you feel the joy of victory. And then you decompile a second one. And a third. And you start to notice that something is wrong with the code.

Every class is a single letter. Every method is called A(). Every meaningful string — URLs, endpoints, error messages, license states — is nowhere in the binary. What you see instead is a sea of calls to a class with a name like a UUID, sitting in a namespace you’ve never heard of, presumably doing something with an 11 KB byte array.

This is the second line of defense: string encryption. The authors knew that anyone who survived the bundle extraction would immediately go hunting for strings — server URLs, error codes, API paths — and they made sure there were none to find statically. The strings exist, but only at runtime, decrypted on demand.

The good news: to the .NET runtime, this is all just metadata. And metadata can be executed.

02Decompiling the managed core

The first step after extraction was to get the whole assembly out as readable source. We used ilspycmd (the ILSpy CLI, v10.1.1.8388) against the recovered DLL:

$ ilspycmd -p -o decompiled NoMercyAI.Visual.dll

The -p flag creates a full project (one .cs per type, plus resources and a project file) instead of a single giant file — much easier to navigate. The resulting tree gave us the shape of the application:

decompiled tree

At a glance: the app layer (VisualColorFilter) is readable — it’s a WPF color-filter overlay with an activation window. The interesting part is the A namespace: a set of classes named A, B, C … through O, with nested types named a, b, c … and every method renamed to A(), a(), B(), b() … The license engine alone (A\M.cs) is 1,427 lines of this.

03Anatomy of the string decryptor

The heart of the obfuscation is a static class whose real runtime name is:

<PrivateImplementationDetails>{22FC3C70-C44A-4F63-B620-9B352B42C44B}.AB1D7EF9-DE7C-42B7-A8C1-82331034674A

ILSpy renders it as AB1D7EF9_002DDE7C_002D42B7_002DA8C1_002D82331034674A (it escapes the <, >, {, }, - characters), but in the actual metadata those are literal characters. That detail will matter later.

The class holds a single giant blob of encrypted data:

internal static byte[] _4 = new byte[11351] { 216, 222, 205, 199, 126, 63, ... };

…and exposes hundreds of parameterless static methods — A(), a(), B(), b(), BA(), BB(), cI(), Dq(), and so on — each of which decrypts one string from that blob and returns it. Calls in the decompiled code look like this:

return b(AB1D7EF9_002DDE7C_002D42B7_002DA8C1_002D82331034674A.Dl(),
         B(AB1D7EF9_002DDE7C_002D42B7_002DA8C1_002D82331034674A.DM(),
           AB1D7EF9_002DDE7C_002D42B7_002DA8C1_002D82331034674A.Dm()));

Every URL, every error code, every status string — gone from static analysis, replaced by a call to a decryptor method.

04The plan: execute the metadata

Reverse-engineering this decryptor statically would mean extracting the algorithm, the key schedule, the offsets — work, but doable. But there’s a much dumber, much more reliable option available to us:

The methods already exist. The .NET runtime can call them.

If we load the DLL into a process with the same runtime version and invoke every one of those parameterless static string-returning methods via reflection, the decryptor does the hard work for us. We don’t need to understand the cipher — we just need to ask the assembly for its own plaintext. Same trick as before, one level up: ask for a copy of the plaintext.

The one requirement: the DLL is a WPF application targeting net8.0-windows, so our runner must target the same framework with WPF enabled — otherwise the assembly won’t load (missing PresentationFramework). A plain console app aimed at net8.0 would refuse to load it.

The project file is minimal:

strdump.csproj 
<!-- must be net8.0-windows + WPF to host the WPF assembly -->
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
    <Nullable>disable</Nullable>
  </PropertyGroup>
</Project>

The runner itself does three jobs: list the types, dump all decryptor methods, and print each decrypted string:

strdump/Program.cs 
// load the obfuscated DLL and decrypt all its strings
using System;
using System.IO;
using System.Linq;
using System.Reflection;

class Program
{
    static int Main(string[] args)
    {
        if (args.Length < 2)
        {
            Console.Error.WriteLine("usage: strdump <dll> <mode> [typeName]");
            return 1;
        }
        string dllPath = Path.GetFullPath(args[0]);
        string mode = args[1];

        Assembly asm;
        try { asm = Assembly.LoadFrom(dllPath); }
        catch (Exception ex)
        { Console.Error.WriteLine("LoadFrom failed: " + ex); return 2; }

        // mode "types" -> enumerate every type in the assembly
        if (mode == "types")
        {
            foreach (var tt in asm.GetTypes().OrderBy(t => t.FullName))
                Console.WriteLine(tt.FullName);
            return 0;
        }

        // mode "dump" -> invoke every static string method on the decryptor
        string typeName = args[2];
        Type t = asm.GetType(typeName);
        if (t == null)
        { Console.Error.WriteLine("type not found: " + typeName); return 3; }

        var methods = t.GetMethods(BindingFlags.Public | BindingFlags.NonPublic | BindingFlags.Static)
            .Where(m => m.ReturnType == typeof(string) && m.GetParameters().Length == 0)
            .OrderBy(m => m.Name, StringComparer.Ordinal);

        int count = 0;
        foreach (var m in methods)
        {
            string val;
            try { val = (string)m.Invoke(null, null); }
            catch (Exception ex)
            { val = "!!ERROR: " + (ex.InnerException?.Message ?? ex.Message); }
            Console.WriteLine(m.Name + "\t" + val);
            count++;
        }
        Console.Error.WriteLine("TOTAL_METHODS=" + count);
        return 0;
    }
}

Two details are worth calling out:

  1. BindingFlags.Public | NonPublic | Static — the decryptor methods are internal, so a default reflection search wouldn’t find them.
  2. m.Invoke(null, null) — the methods are parameterless statics, so no target instance and no arguments. Just call them.

05The type-name gotcha

The first attempt to dump failed with type not found. The reason is exactly the naming detail mentioned earlier. ILSpy renders the runtime name with escaped underscores:

_003CPrivateImplementationDetails_003E_007B22FC3C70_002D...

…but that’s just ILSpy’s ASCII-safe rendering of the name. In the actual metadata, the characters are literal:

<PrivateImplementationDetails>{22FC3C70-C44A-4F63-B620-9B352B42C44B}.AB1D7EF9-DE7C-42B7-A8C1-82331034674A

So asm.GetType() needs the real name with the raw <, >, {, }, . characters. A quick asm.GetTypes() dump confirmed it. Easy fix, easy lesson: the decompiler’s rendering of a type name is not the type name.

Part 3The License System

01Introduction

By now we have everything on disk: the extracted DLL, a full decompilation, and 453 plaintext strings. We know the server (nomercyai.tech), the endpoints, the protocol markers, and the public key. All the ingredients are in hand — so what does the gate actually look like?

This is the interesting part. Because the license system is not a single if statement you flip. It’s a small state machine that:

  1. Binds every session to the device and the binary — a response is only valid if it matches the nonce, the device ID, the device key, the client build and a binary hash.
  2. Verifies server responses cryptographically — ECDSA P-256, private key on the server, public key in the client.
  3. Keeps re-validating forever — a one-minute timer re-checks with the server for the entire lifetime of the process.
  4. Survives brief outages — a 15-hour offline grace window, tied to the last successful validation.
  5. Hates debuggers and patch jobs — anti-debug checks and a 4-minute “lease” that must be re-armed by each successful validation.

None of this is unbeatable in an absolute sense. But it’s worth understanding exactly where every decision is made — because that’s where the design lives and dies.

02The trust model

The core idea is asymmetric. The server holds the signing private key; the client embeds only the public key:

MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAET a6dZO3clRgBl96BdtrDBpaTjNBJmYRVqkDOmq6U8q3xTgDjd3xk5YDu2PDrkaNITYBzVj0d3byiaQbuXEleHQ==

That’s a SubjectPublicKeyInfo blob for an EC P-256 key (ec-p256-v1). Any response from the server — a signed license payload, a revocation status, an update manifest — carries a signature the client verifies against this key:

A/N.cs — signature verification 
using ECDsa eCDsa = ECDsa.Create();
eCDsa.ImportSubjectPublicKeyInfo(array, out _);
return eCDsa.VerifyData(
    Encoding.UTF8.GetBytes(P_0),
    signature,
    HashAlgorithmName.SHA256,
    DSASignatureFormat.Rfc3279DerSequence);

Consequence: a valid license can only be produced by someone who holds the server’s private key. The client can’t mint its own — it can only judge what the server sends. Any bypass, therefore, lives entirely in how the client judges, and in what happens between validations.

03The state

Three objects carry the whole system:

ObjectRole
kthe license: status, issuedTo, expiresAt, daysRemaining, maxDevices, isLifetime, plus a lastValidated timestamp. Valid = status == "active" && expiresAt > lastValidated
cthe activation cache: token, deviceId, license fields, lastValidatedAtUtc, offlineValidUntilUtc, device key ID, protocol version
lthe result: valid (bool), status code (e.g. license_expired), user-facing message, and the license

The cache is written to disk as activation.dat, DPAPI-protected (ProtectedData.Protect under the current user) so it can’t be forged by writing a JSON file by hand:

A/M.cs — persist the activation cache 
Directory.CreateDirectory(M.m_a);
byte[] array = ProtectedData.Protect(
    JsonSerializer.SerializeToUtf8Bytes(P_0, M.m_A),
    M.m_A,
    DataProtectionScope.CurrentUser);
// write atomically: tmp file + File.Move(overwrite: true)

The device identity lives separately in device-id.dat, also DPAPI-protected — a 64-hex-char random string generated on first run.

04The startup gate

The entry point is App’s startup handler in VisualColorFilter\App.cs. The flow is short:

  1. Install exception handlers.
  2. Take a single-instance Mutex.
  3. Kick off M.A() (validate with the cached token) — and if a splash is enabled, show it while waiting.
  4. Evaluate the result:
VisualColorFilter/App.cs — the gate 
private static bool A(l P_0)
{
    if (P_0.A() && P_0.A != null)   // valid && license != null
    {
        return true;
    }
    ActivationWindow activationWindow = new ActivationWindow(P_0.B());
    if (activationWindow.ShowDialog() == true)
    {
        return activationWindow.A != null;   // a license came back from the dialog
    }
    return false;
}

If the gate returns false, the app Shutdown()s. If true, a MainWindow is created and the tray NotifyIcon is initialized. The first decision point is literally this three-line method: valid result + non-null license.

  "deviceKeyId": "...",
  "requestTime": "...",
  "deviceProof": "..."
}

Note the last five fields: this isn’t just key + deviceId. The client generates a device key pair, proves possession of it (deviceProof), and sends the public half — so the server can bind the license to a cryptographic device identity, not just a random string that could be copied to another machine.

The response is verified in M.A(response, nonce, deviceId, deviceKeyId, ...) — the signed-payload validator:

  1. protocol == "ec-p256-v1" and the ECDSA signature verifies over the signed data.
  2. The signed data (newline-delimited key=value lines, tagged nmv-license-v1 or nmv-license-v2) must contain: protocolVersion == 2, nonce == the one we just sent (anti-replay), device == our deviceId, deviceKey == our device key ID, values matching our clientBuildId and binaryHash, status == "active", expiresAt / maxDevices / isLifetime matching the license JSON, issuedTo matching, and serverTime within 10 minutes of our clock.
  3. The license JSON must be internally consistent with the signed fields.

Only then is the cache written, the lease armed, and a valid l returned.

Consequence: a captured activation.dat from another machine dies on the device/deviceKey/binaryHash bindings — even before the server gets a say.

06The one-minute loop

The part most people forget about. Once in MainWindow, App starts a DispatcherTimer:

VisualColorFilter/App.cs — re-validation loop 
this.m_A = new DispatcherTimer { Interval = TimeSpan.FromMinutes(1.0) };
this.m_A.Tick += A;
this.m_A.Start();

Every tick calls M.A() again — the validate overload — which re-POSTs the cached token to api/licenses/validate, re-verifies the signed response, and updates the cache. The tick handler then applies the three-strike rule:

  • Transient failures (network, timeout, unknown) — status codes like validate_network / validate_timeout — are retried, up to 3 consecutive ticks.
  • Hard failures (invalid, expired, revoked) — are terminal immediately: the window is hidden, the app re-opens ActivationWindow, and if the user can’t produce a valid license, the app exits.

So even a flawless startup check is not enough: the license must survive re-validation every minute, forever. Kill the server check and you have ~60 seconds before the timer comes knocking.

07The offline grace window

Network failures are the one case where the app is forgiving — by design. When the server is unreachable (timeout, 429, 5xx), M.A() falls back to a(c2), the offline path over the cached activation:

A/M.cs — offline grace path 
DateTime utcNow   = DateTime.UtcNow;
DateTime dateTime  = P_0.C.ToUniversalTime();                    // lastValidated
DateTime dateTime2 = P_0.D == default
    ? dateTime.AddHours(15.0)                                    // offlineValidUntil
    : P_0.D.ToUniversalTime();

if (dateTime == default || utcNow < dateTime - M.m_A || utcNow > dateTime2)
    return null;                                                 // outside the window

if (P_0.B.ToUniversalTime() <= utcNow) return null;              // already expired
if (P_0.c == default) return null;                               // never validated

bool flag = P_0.B.ToUniversalTime().Year >= 9000;                // lifetime key

The window is [lastValidated − tolerance, lastValidated + 15h]:

  • lastValidated is the server-provided time from the last successful validation (not local time).
  • offlineValidUntilUtc = lastValidated + 15h.
  • expiresAt must still be in the future.
  • A license with expiresAt in the year 9000 is treated as lifetime (isLifetime).

If the offline check passes, the app builds an active license from the cache, arms the lease, and keeps running. That’s the product’s offline-usability feature — and, as always with grace windows, it’s also the one place where time itself is the only other participant in the decision.

08Anti-debug and the lease

Two guards make runtime patching awkward:

Anti-debug (O.A()) — called at the start of both activation and validation, before any network I/O:

A/O.cs 
internal static void A()
{
    if (Debugger.IsAttached || a())     // a() -> IsDebuggerPresent / CheckRemoteDebuggerPresent
    {
        L.a();
        throw new SecurityException(...);
    }
}

Attach a debugger and the next validation throws SecurityException. This is why our workflow was: static analysis + executing metadata in a separate process, never debugging the live app.

The lease (L) — a timer-based guard armed only by success:

A/L.cs 
private const long m_A = 240000L;   // 4 minutes

internal static void B()
{
    O.A();
    long elapsed = Environment.TickCount64 - Interlocked.Read(ref m_a);
    if (Volatile.Read(ref m_A) != 1 || elapsed < 0 || elapsed > 240000)
        throw new SecurityException(...);   // "signed license lease missing or expired"
}

L.A() (arm) is called inside the successful paths of activation, validation, and offline grace. Any runtime path that needs a fresh lease must find one armed within the last 4 minutes. This is the subtle one: bypassing the validation check in a way that skips L.A() leaves the lease to expire, and the next runtime check throws. A “return true” patch that ignores the lease doesn’t survive a single minute — the very timer meant to keep the license honest is also what keeps the lease fresh.

Binary binding — the requests and signed responses are bound to a clientBuildId and binaryHash derived from the client itself. A modified binary presents a different fingerprint, which the server can (and does) verify server-side. Whatever you change locally, the server still decides whether to sign a response for that fingerprint.

09The decision points, mapped

Every gate we found, in one table:

#WhereWhat decidesOn failure

3M.A() validate (1-min timer)re-verify server response, update cache3 transient strikes or 1 hard failure → re-activate

The key insight for anyone reading this as a design reference: the decisions are layered and self-reinforcing. Startup, timer, offline window, lease and anti-debug each require the others to have happened. Defeating one leaves the other four standing, and the server’s signature sits at the root — every local path ultimately depends on having received a signed, device-bound, current license.

10What’s Next?

This closes the three-part series. We went from a truncated 77 MB binary, to a clean extracted DLL, to 453 decrypted strings, to a full map of a server-signed, device-bound, clock-aware license system — every endpoint, every state, every decision point.

The technical story that’s often told about “impenetrable” protection is really just this: a sequence of boring, correct decisions stacked on top of each other. And the practical lesson of the whole exercise is the one we kept coming back to — the best way through a wall is usually to ask the target for its own plaintext, one layer at a time.

Part 4Hardening the System

01Introduction — a map is a two-way street

Everything in Parts 1–3 was an attacker’s map. But a map doesn’t take sides: every weakness we found is also an unpatched hole the owner can close. Nothing here is exotic — it’s the same boring, layered design we spent three parts dissecting, done properly.

The honest framing first: a client that ships its own decryption keys can never be truly secure. The goal is never “impenetrable” — it’s cost. Each fix raises the time, tooling and skill needed to get past it, until the effort stops being worth the reward. That’s the standard we design to.

02The weaknesses, grouped

Everything we found collapses into five structural problems:

#WeaknessWhere it bites
1Payload is recoverableTruncated bundle, headerless table, raw DEFLATE, no encryption (Part 1)
2“Obfuscation” is a static cipherKey material embedded in the assembly; reflection dumps everything (Part 2)
3Decisions run client-sideThe client owns the validation, the grace window, the lease and the timer (Part 3)
4Device binding is a DPAPI fileactivation.dat / device-id.dat are machine-user DPAPI — migratable by the same user
5Anti-debug is cosmeticDebugger.IsAttached / IsDebuggerPresent are bypassed in minutes

The fixes below each map to one of these five.

03Fix 1 — Encrypt the payload (kills weakness 1)

Part 1 was possible because the bundle stored everything in raw DEFLATE with no footer validation. The fix is to make the managed payload not exist until runtime:

  1. Use .NET 7+ single-file encryption (IncludeAllContentForSelfExtract + published single-file with encryption) so the IL is encrypted on disk and decrypted only in the native host at load.
  2. Move the key out of the file. Do not embed a static key next to the blob. Derive it from the native host, the signing certificate chain, or a server handshake — anything that isn’t a constant in the same binary.
  3. Anti-dump in the native host: wipe the decrypted mapping after load where feasible, hook NtQueryVirtualMemory/minidump paths, and register a minidump callback that scrubs managed heaps before dump.
  4. Validate the headerless table. Part 1 worked because there was no footer check — add the 0x8b12 footer and verify every entry hash at load.

Effort: medium · Impact: very high — it re-does Part 1 from scratch.

04Fix 2 — Real constant protection (kills weakness 2)

Part 2 took one afternoon because the “obfuscator” was a static dictionary: one 11,351-byte blob, one decryptor class, every string in the clear in memory. The fix is to stop shipping the key:

  1. Context-keyed encryption. Derive each string’s key from its method (method name + body hash), so a single dump no longer works — you’d need per-method keys.
  2. No global blob. Split the key material across the assembly, generated per-build, so a prior build’s keys are dead.
  3. Lazy decrypt-and-free. Decrypt only when first used, then wipe the buffer; keep strings out of the “all strings in memory” state that a strings-style sweep finds.
  4. Use a real obfuscator (ConfuserEx, Agile.NET, Eziriz) for control-flow + constants, and re-run it per release. Caveat: obfuscation raises cost; it is not a boundary.

Effort: low–medium · Impact: high — kills the reflection dump we did in Part 2.

05Fix 3 — Move decisions server-side (kills weakness 3, the big one)

The structural flaw in Part 3 is that the client decides. The server signs, but the client judges — and a judge you control can be persuaded. The fix is to stop trusting the client’s judgment for the things that matter:

  1. Short-lived session tickets, not long-lived licenses. Activate once, receive a signed ticket with a 5–15 minute TTL. Every feature call re-presents the ticket; the server re-signs or rejects. There is no “cache” to fix because there’s nothing long-lived to cache.
  2. Streaming / challenge responses. Each validation round includes a server-issued random nonce the client must include in the next request; responses are bound to that nonce chain. A replayed or fabricated session dies in one round.
  3. Online enforcement for the crown jewels. The offline path is where client-side trust lives. Make core functionality (exports, filters) require a fresh server session; degrade gracefully (watermark, read-only) offline instead of full unlock.
  4. Server-side binary fingerprint. Store the client’s binaryHash server-side and refuse to sign for unknown/modified hashes — the check can’t be patched client-side because the server enforces it.
  5. Nonce monotonicity. Track a server-side counter per device; reject out-of-order validation (kills the “roll back time/state” class of attacks).

Effort: high · Impact: the highest — this is the only fix that removes the client as the ultimate decision-maker.

06Fix 4 — Bind to hardware, not a DPAPI file (kills weakness 4)

activation.dat and device-id.dat are DPAPI CurrentUser blobs. That protects against casual text editors, but the same Windows user can migrate them to another machine and they decrypt fine. Fix:

  1. TPM-backed keys. Store the device key in the TPM (NCrypt/TPM 2.0, non-exportable) and sign a proof with it on every activation. Copying files no longer copies the ability to sign.
  2. Windows Hello / hardware attestation where acceptable — the strongest client-side anchor Windows gives you without a driver.
  3. Dual factor on license binding: bind to (a) the TPM key ID and (b) a server-registered device record, so even a cloned disk fails the server-side device check.
  4. Kill the migration vector explicitly: server-side detect and reject a device record that suddenly reappears with a different hardware profile.

Effort: medium–high · Impact: high — removes the “copy activation.dat to another PC” scenario for real.

07Fix 5 — Shrink and complicate the grace window

Part 3 showed a 15-hour offline grace: [lastValidated − tolerance, lastValidated + 15h], plus a 3-strike transient rule. That’s a big, forgiving surface. Fix:

  1. Tighten the window (e.g., 4 hours) and make the tolerance asymmetric — an old lastValidated is suspicious, not forgivable.
  2. Signed offline extensions. When validating online, also issue a short, signed offline-extension token the client may use once offline. No online validation → no fresh token → offline mode dies when the old one expires. The grace now requires the server’s signature instead of just the client’s clock.
  3. Anchored clock, not client clock. Never trust DateTime.UtcNow from the host for decisions; always evaluate against the last server-provided time plus elapsed-time measurement. Lifetime keys (Year ≥ 9000) should be re-verified online periodically — a lifetime license should not also be an offline-forever license.
  4. Strike counting server-side. Have the client report transient failures; decide the “3 strikes” policy on the server, so the retry budget can’t be stretched by patching a constant.

Effort: medium · Impact: high — removes the cleanest “just go offline” bypass.

08Fix 6 — Make the lease meaningful

The 240-second lease (L.A()/L.B()) is armed by the successful paths — good — but it’s a client-side timer. A patch that calls L.A() unconditionally (or NOPs L.B()) makes it cosmetic. Fix:

  1. Derive the lease from the signed response, not a local call. The lease token should be a field inside the server’s signed payload (session id + expiry). No valid signature → no lease token, regardless of what the client code does.
  2. Cross-check the lease with the timer’s validation. Every 1-minute re-validation must re-arm the lease from a fresh signed response; if validation is skipped, the lease expires and the next check fails.
  3. Anti-tamper coverage: any bypass must now keep the anti-debug, the lease and the timer consistent simultaneously — three clocks instead of one.

Effort: low · Impact: medium — cheap, and it de-values naive NOP/ret patches.

09Fix 7 — Enforce binary integrity beyond a local hash

The clientBuildId/binaryHash binding is already in the requests (Part 3) — the flaw is that the client computes it. Fix:

  1. Authenticode + runtime checksums. Verify the executing assembly’s Authenticode signature at startup, and checksum critical methods’ IL against expected values (or use an obfuscator’s anti-tamper).
  2. Server-side verification. Recompute/hash on the server where possible (device attestation, or signed hardware counters). Server rejects unknown hashes before signing anything.
  3. Split the hash source. Compute the hash from multiple sources (file bytes, loaded module base, runtime config) and combine — a single-file patch becomes a multi-point patch.

Effort: medium · Impact: medium–high — makes “patch one byte, keep the license” materially harder.

10Fix 8 — Real anti-debug (kills weakness 5)

Debugger.IsAttached and IsDebuggerPresent are two Win32 reads; every debugger removes them in minutes. If you’re going to ship anti-debug at all, raise the bar:

  1. DBI detection: hardware breakpoints (GetThreadContext/SetThreadContext inspection), timing checks, NtQueryInformationProcess for ProcessDebugPort/ProcessDebugObjectHandle, and scanning for known debugger DLLs.
  2. Chain to the lease. The nastiest pattern is the one this product already half-has: don’t crash on debug — just stop re-arming. Debug attach → validation never completes → lease expires → app refuses. The attacker must now disable anti-debug and fake the lease chain.
  3. Honest trade-off note: comprehensive anti-debug belongs in a native host or kernel component, and even then it’s bypassable. Budget it as cost-raising, not as a wall.

Effort: medium · Impact: medium — but cheap to chain onto Fix 6.

11Fix 9 — Server-side operations

Everything client-side is secondary to how the server behaves. The cheapest wins are here:

  1. One-time nonces with server-side storage. Reject any nonce seen twice (Part 3 already checks the client’s nonce — extend it to a server-side replay cache).
  2. Rate-limit and throttle activation/validation per key, per device, per IP. Detect the activation hammer you’d expect from key-sharing.
  3. Near-real-time revocation. api/licenses/revocation-status is polled by the client (and the client can be told to ignore it). Move to server-enforced sessions (Fix 3) so revocation means “server stops signing” — instant and client-independent.
  4. Key hygiene: separate keys per environment, rotate the signing key, and keep the private key in a KMS/HSM — never next to the public key in a client binary.
  5. Anomaly detection: device-per-key ratio, activation velocity, offline→online pattern — the data this system already generates is enough to flag abuse without any client changes.

Effort: low–medium · Impact: very high — a good server costs little and invalidates most client-side games.

13Closing

The three parts before this one read like an attacker’s playbook. This part is the owner’s playbook. The two share every fact — which is the point: the defense is the attack, inverted.

And the honest summary, once more: no client-side scheme is unbreakable, because the client always carries the keys to its own cage. What a product can do — and what this list does — is push each attack until it costs more than the product is worth. That’s not paranoia; that’s the design.
