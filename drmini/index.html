A PE protector that will not hand you a broken binary.

DRMini rewrites compiled Windows x86-64 executables and DLLs: strings encrypted, imports hidden, code virtualized, watermark stamped. It analyses the image first, then applies only what the binary can survive.

Protection stack

Composable passes, not one opaque preset.

Build a focused profile instead of turning on everything. Every protection below is a switch in drmini.json.

Why it is built this way

Stability is a requirement, not an afterthought.

Obfuscation only matters if the protected binary still behaves like the original. An unstable protector costs more in re-testing than it ever gains in resistance.

  • Analysis before transformation

    The code section, import directory, bound imports, export table, .NET metadata, dynamic base, relocations and existing TLS callbacks are all inspected before a single byte is rewritten. What it finds is what decides the profile.

  • Graceful degradation

    When a pass would produce an executable that cannot start, it is disabled instead of applied. The reason is recorded and printed, so there is never a question about what you actually got.

  • String detection is triple-checked

    Candidate strings are confirmed with a dedicated pass before anything is encrypted, so instruction bytes and pointers that merely look like text do not get destroyed along with them.

  • Nothing happens silently

    Symbols stripped, sections removed, strings encrypted, imports hidden, bytes encrypted, regions virtualized, watermark written. Every count ends up in the report.

Architectures

x86-64

Native Windows PE, no emulation layer in between.

Binary formats

EXE, DLL

Any PE the loader will accept, including signed and .NET images.

Toolchain

MSVC, vcpkg

C++ with Zydis for disassembly and the PE work.

Integration

Drag and drop

One executable, one JSON file, no installer and no runtime dependency.

A protector that breaks your build is a liability.

That is why every protection is independently toggleable, why the profile is explicit, and why anything the image cannot support is reported rather than forced. A clean report is a better outcome than a silent failure.

The pipeline

Ten stages, in the order the engine runs them.

Each stage reports progress and each one can degrade instead of failing. This is what actually happens when you drop a binary on it.

    Workflow
    
        
    From binary to protected build.
    
        
    No installer, no account, no upload. The whole thing happens on your machine.
    
      
    
      
    
        
    
          01
          
    Drop it in
    
          
    Drag an executable onto drmini.exe, or pass the path as an argument. The output is written next to the input with a .drmini.exe suffix.
    
        
    
        
    
          02
          
    Tune the profile
    
          
    drmini.json lives next to the executable. Turn on what you need, leave the rest off, and re-run if the report says something was skipped.
    
        
    
        
    
          03
          
    Read the report
    
          
    A single summary line tells you what was stripped, encrypted, hidden, virtualized and stamped, plus every pass that had to be dropped to keep the binary working.
